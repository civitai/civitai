# Retool DB — the tables that actually matter

Retool's own Postgres (`retool_db` in the app exports) holds moderation data that never existed in
Civitai's database.

> **Superseded 2026-08-21.** The two databases were consolidated. `getModeratorDb()` reads
> `MODERATOR_DATABASE_URL`; `RETOOL_DATABASE_URL` is retired. Every mention of it below is historical.

**The moderator app reads and writes it directly**, through `getModeratorDb()` — `RETOOL_DATABASE_URL`
points here for now. So porting a `retool_db`-backed feature needs no data migration first: Retool and
the moderator app share these tables during the transition, which is what allows an incremental cutover.
Later the tables move to a database of their own and only the connection string changes.

What remains is a **data-quality** migration (attribution, types, the `ReToolActions` decision), not a
prerequisite for building.

The database has **43 tables**. Only **7** are touched by the three apps being migrated — the rest are
bot scratch space, sample data, temp tables and abandoned experiments. Generated by cross-referencing
each export's `retool_db` queries against the live schema; regenerate with
[`retool-db.mjs`](../../../.claude/skills/retool-migration/retool-db.mjs).

## Must migrate

Real moderation history with no home in Civitai's schema.

### `UserNotes` — 56,339 rows

Free-text moderator notes per user, plus two flags that act as moderation state.

| column | type |
| --- | --- |
| `id` | integer |
| `userId` | integer |
| `notes` | text |
| `lastUpdate` | timestamptz |
| `lastUpdateBy` | text — moderator **name**, not an id |
| `spamWhitelist` | boolean |
| `deservedMute` | boolean |

Used by: User Lookup (`SelectUserNotes`, `InsertUpdateUserNotes`, `UsersWithNotes`), User Reports
(`RetoolNotes`). Ticket §1.2 "mod notes".

`spamWhitelist` and `deservedMute` are behaviour flags hiding in a notes table — decide whether they
become `User` columns or move with the notes.

### `UserStrikes` — 12,771 rows

The strike system. Nothing equivalent exists in Civitai's schema.

| column | type |
| --- | --- |
| `id` | integer |
| `userId` | integer |
| `createdAt` | timestamptz |
| `createdBy` | text — moderator **name** |
| `reason` | text |

Used by: User Lookup (`UserStrikes`, `InsertStrike`, `LogStrike`), User Reports (same). Ticket §1.2
"strike account".

### `TimedMutes` — 0 rows

Scheduled mutes with an expiry. **Currently empty** — either unused or recently cleared. Confirm with
the moderation team before building for it; an empty table may mean the feature is dead.

| column | type |
| --- | --- |
| `userId` | **text** (inconsistent with `UserNotes.userId` integer) |
| `muteStart` / `muteEnd` | timestamptz |
| `createdBy` | text |
| `muteReason` | text |
| `isMuted` | boolean |

### `ModerationImageHelp` — 37 rows

Queue where a moderator asks colleagues for a second opinion on images. `imageIds` is a jsonb array.

| column | type |
| --- | --- |
| `createdBy` / `handledBy` | text |
| `imageIds` | jsonb |
| `type` | enum |
| `isHandled` | boolean |
| `createdAt` / `handledAt` | timestamptz |

Used by: Moderation Status (`GetHelpers`, `UpdateHelpRequest`). Small and self-contained — the cheapest
of these to move.

## Audit log — migrate or archive

### `ReToolActions` — 131,024 rows

Every action taken through Retool. Columns are `Event`, `User`, `App`, `ActionType` — free text, no
foreign keys, and queried with `LIKE '%' || userId || '%'`, so the user reference is embedded in a
string.

This is the closest thing to a moderator audit trail predating `ModActivity` being append-only. Decide:
migrate into `ModActivity`, keep as a read-only archive, or drop. It cannot be joined reliably as-is.

## Not referenced by anything we hold

The remaining tables are untouched by the three exports *and* absent from the migration ticket:
`FrontPageTimers` (67k), `ModerationSHA` (30k), `Mods_TaskTimers` (19k), the `CivBot_*`/`ModBot_*`
tables, `sample_*`/`test_*`/`Temp_*`, `ModNotes` (0 rows, superseded by `UserNotes`), and assorted
one-off reports.

Treat this as "unaccounted for", not "safe to delete" — a later export may claim some of them. Re-run
the cross-reference whenever one arrives.

`FrontPageTimers` and `Mods_TaskTimers` *are* written by Moderation Status's timer queries, which are
Retool workflow plumbing measuring how long moderators take rather than tooling anyone uses. Confirm
before discarding.

## Two schema problems to resolve before designing the target tables

1. **Moderators are identified by name, not id — and the names mostly do not resolve.**
   `createdBy`, `lastUpdateBy`, `handledBy` and `ReToolActions.User` are free text holding *Retool
   account display names* ("Maxfield Hulker", "Cameron Jackson"), not Civitai usernames.

   Measured 2026-08-06: **37 distinct identifiers across `UserNotes` + `UserStrikes`; only 5 match a
   Civitai moderator account** by `username` or `name` (24 moderator accounts exist). None are emails.

   So ~32 cannot be resolved automatically, and they cover the bulk of 56,339 notes and 12,771 strikes.
   The migration needs a **hand-built name → userId mapping table**, agreed with the moderation team,
   before attribution can be preserved. Without it, "who wrote this note" is lost for most rows — which
   is much of why the notes are worth keeping.

   **The mapping now exists** — see [moderator-id-mapping.md](moderator-id-mapping.md). It covers 72%
   of records by exact name, 21% via short forms that need confirming, and leaves 6% unmapped (almost
   all of it one former moderator).
2. **`TimedMutes.userId` is text** while `UserNotes.userId` and `UserStrikes.userId` are integer. Cast
   during migration and check for non-numeric values first.

## Querying it

```bash
cd .claude/skills/retool-migration && npm install   # once
cp .env.example .env                                # add MODERATOR_DATABASE_URL
node retool-db.mjs --tables
node retool-db.mjs --describe UserStrikes
node retool-db.mjs "SELECT * FROM \"UserNotes\" LIMIT 5"
```

`retool-db.mjs` is read-only — it exists for scoping and schema questions. **The app itself reads *and
writes* this database** through `getModeratorDb()`, on the same `MODERATOR_DATABASE_URL`. See the
skill's moderator-database section.
