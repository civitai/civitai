# Knights of New Order: gold conversion

Moved from `apps/knights/CLAUDE.md`. Code lives in `apps/knights/src/lib/server/conversion`.

Migrations `20261218120000_knights_v2_conversion` (`NewOrderPlayer.goldConverted`, `KnightsGoldConversion`) and `20261223120000_knights_v2_drop_gold_clearing` (drops `NewOrderPlayer.goldCleared`, `KnightsDetectionRun`, `KnightsGoldClearing`), both applied by hand. Rate, minimum, retry age and the tick's retry bounds: `config.ts`. Deploy order on prod: the conversion migration (after `20261213120000_knights_v2_progression`) and the main app carrying the new `NewOrderPlayer` gold columns are already live. For the drop: deploy the Knights app first (it no longer reads `goldCleared` or detection runs; the previous main app's reset still zeroes `goldEarned`, so convertible gold stays correct), then the main app, then apply the drop migration by hand.
- Recent conversions (`recent.ts`): the player's latest 10 `KnightsGoldConversion` rows (newest first, by `playerId_createdAt` index), listed on `/gold` with status pending / paid / failed.
- Balances (`balance.ts`): pending (`goldPending`), convertible (`goldEarned - goldConverted`), frozen, on its way (reserved by an unconfirmed conversion) and converted (paid only). Gold is convertible as soon as it is earned (a vote graded correct, a completed Watch). A held player (payout block set, or banned) has every unconverted gold frozen and none convertible; nothing is lost, and a released player's gold shows as convertible again. A career reset (`resetPlayer`) forfeits unconverted gold, as it does the old counters: pending goes to 0, earned drops to what was converted or reserved, and a reservation made before the reset that Buzz later refuses is forfeited rather than given back (the player is told). `resetPlayer` sets `startAt` from the database clock under the player row lock, and conversions are stamped on that clock, so the two are ordered by the lock.
- Label pass (`label-pass.ts`): `POST /api/jobs/tick` runs `runLabelPass` every tick within a time budget; it sets up the question rules only for a kind of vote that has labels waiting. Everything it writes is keyed on the data (unlabelled votes), so a pass cut short resumes on the next tick and a repeat writes nothing.
- Labels (`labels.ts`): one `knight` label per graded rating vote (`settledAt`) and per given yes/no answer (`createdAt`), for players not held, written through `label_store.record_label` (shape: `docs/features/label-store.md`). `KnightsVote.labelled` marks done. A held player's votes stay unlabelled because the store never retracts a label. A vote the store refused stays unlabelled and is retried once 10 minutes have passed since its last failure, up to 5 refusals; when every vote in a raising batch raises the store is taken to be down and nothing is recorded against the votes; a batch that raises is retried vote by vote so one vote cannot block the rest (`labelFailures` in the result; `label_store.record_failure` has the reason). The rating write-back (`setNsfwLevelKono`) does not wait for this.
- Converting (`convert.ts`, `/gold`): one transaction locks the player row, checks not held and the minimum, writes a `pending` `KnightsGoldConversion` with its own `externalTransactionId` and adds the gold to `goldConverted`. Then Buzz is asked (`buzz.ts`, through `@civitai/buzz`) outside the transaction with that key.
  - `paid`: the Buzz transaction id is stored and never overwritten; a 409 (key already paid) leaves it empty.
  - Unknown outcome (timeout, network, 5xx, 408, 429): the row stays `pending` with the gold reserved. The player's next Convert, or the tick (`retryPendingConversions`: not held, bounded by count and time, skipped with a warning when `BUZZ_ENDPOINT` is unset), sends the same key. Retries take the least recently attempted first and skip rows tried within the retry age, so a stuck one cannot hold up the rest; none is started that could not finish inside the tick's budget. Convert is refused, and nothing reserved, while `BUZZ_ENDPOINT` is unset.
  - `failed`: any other 4xx. The reservation is released in the same transaction, the player sees a failure message and it is logged.
- Switch: `KNIGHTS_CONVERSION_ENABLED` (`conversionEnabled()` in `runtime.ts`) must be exactly `true` for gold to convert; it is off by default. Off: `/gold` shows balances but refuses Convert (403, nothing reserved), `/play` hides the link and the tick skips conversion retries; gold still accrues and the label pass still writes labels.
- Logging goes through `src/lib/server/axiom.ts`, a forwarding file in the datastream ledger test. The label pass logs `knights-label-pass` with the Buzz converted per UTC day when it wrote or failed a label.
- Tests: `convert.pglite.test.ts`, `label-pass.pglite.test.ts` (boots the real label store migration via `bootLabelStore`).
