# apps/knights

**Follow [`docs/svelte-app-standard.md`](../../docs/svelte-app-standard.md)** for runes, derive-the-promise,
keyed loops, form actions, comments and the review agents. Every SvelteKit app here shares it.

Knights of New Order as its own SvelteKit spoke, served at knights.civitai.com. It is deliberately free of
civitai.com's styling: plain CSS in `src/global.css`, no Mantine, no `@civitai/ui`, no Tailwind.

The game is moving here from the main Next.js app: `src/components/Games`,
`src/server/services/games/new-order.service.ts` and `src/server/jobs/new-order-jobs.ts`. It keeps using the main
Postgres through `@civitai/db/kysely` and the existing `NewOrderPlayer` tables; do not add a second database.

## Access gate

Flipt flag `knights-of-new-order-app` (`KNIGHTS_APP_FLAG` in `src/lib/server/access.ts`), evaluated per user
through `@civitai/flipt`; the `testers` segment is configured in Flipt, not here. `src/hooks.server.ts` runs the
`@civitai/auth` spoke guard, then `accessFor` -> `decideAccess` (`src/lib/access.ts`, pure and unit-tested):

- anonymous: `/` is the welcome page (`routes/+page.svelte`, `lib/welcome.ts`) and a page load anywhere else is redirected to `/?next=<path>` (a URL no route answers gets the 404 instead, `showsNotFound`); its "Sign in with Civitai" is the guard's own login URL with the sanitised `next` as return-to. A signed-in visitor to `/` runs the checks below and the page's load redirects them to `/home`, or to `?next=` when that is an internal path (`safeNext`). API and non-page requests keep the hub redirect
- moderator: always allowed
- anyone else: allowed iff the flag is on for them; flag missing or Flipt down fails closed
- denied: a plain "not yet open" page (403)

To open the app to everyone, drop the `accessFor` check in the hook.

## Queue (`src/lib/server/queue`)

Tables `KnightsQuestion`, `KnightsQueueItem` and `KnightsVote` (migration `20261210120000_knights_v2_tables`, applied by hand).
Everything takes the Kysely client as an argument so `queue.pglite.test.ts` runs the real service and the real migration
SQL on PGlite.

- `enqueueItem`: an item's `minRank` defaults to its question's, an override wins; `votesNeeded` can only lower the votes a stage needs (`STAGE_RULES`), never raise them. `minRank` must be a stage rank (Knight, Templar, Paladin); anything else throws.
- `getFeed`: the highest stage the player may judge with an unjudged open item, from a per-stage window read per level bucket (`feed.ts`: `bucketWindowSize` per bucket and tier,
  PG/PG-13/R/X/XXX by prediction else image level, plus a no-bucket group; `bucketLevelSql` is `itemBucket` in SQL). Each pick draws a bucket with equal probability among those with candidates, avoiding the
  player's last judged buckets when it can; within the bucket, items escalated in the last day first, then priority, in a per-player hash order, and about one pick in ten takes the bucket's oldest. An image the player judged for the question is never
  served again, at any stage or earlier item (served by the `("playerId","imageId")` index). `canVote` (`ranks.ts`, shared with `castVote`) says which ranks judge a stage; Inquisitors and Acolytes get no feed. It never selects the
  rating or a hidden check, and serves only images the public feeds would show (`servableImage` in `@civitai/db/knights`).
- `castVote`: refuses what the feed would not serve, then one transaction that locks the item row, refuses a vote that would weigh 0 (`no-weight`; a held player's is stored at weight 0 instead, and `decideChoice`/`decideYesNo`/`escalateExpired` ignore weight 0, so it never moves a verdict; clearing the hold does not re-weight it), writes the ledger row, and decides the votes cast at the item's current stage
  only, by `STAGE_RULES` (`stage-rules.ts`): Knight 4 unanimous, then 75% (to 10), Templar 3 unanimous, then 75% (to 6), Paladin 2 unanimous, then 75% (to 4). No agreement at the maximum moves `minRank` Knight -> Templar -> Paladin -> Inquisitor
  (`ESCALATION_PATH`, stamps `escalatedAt`, migration `20261210120000_knights_v2_tables`, by hand); `status = 'Inquisitor'` is what the moderator app reads. A rating far below the image's, or a Blocked consensus, also goes
  there. Earlier-stage votes stay `pending`, graded by the final value. Escalation skips stages nobody can serve: the next stage with an eligible player at that rank or higher (voted within `ACTIVE_PLAYER_DAYS` = 14, not reset-pending; `nextStaffedRank`/`staffedRanks`), else the Inquisitors. An item that lapses (`expiresAt`) with no vote at its stage is extended a window at a time at the same stage until two stage windows after it entered the stage (`extended` in the tick response); after that it closes as `Closed`/`reason = 'expired'` (no label, no write-back, leftover votes inconclusive; `expired` in the tick response). At an unserved stage it is handed up, or expires when that would reach the Inquisitors. Detail: [`docs/features/knights-queue-escalation.md`](../../docs/features/knights-queue-escalation.md).
- A settled rating is written by `main-app.ts` via the main app's `/api/mod/image/kono-set-nsfw-level` (activity
  `setNsfwLevelKono`; authenticated with `WEBHOOK_TOKEN` in the `x-webhook-token` header, env in `.env.example`) after the vote commits, with no lock held. That endpoint is the gate: it writes only onto an image
  that exists, has no block marker and is unlocked or Knights-locked, and answers 200 `applied` or `skipped`
  (`missing` | `blocked` | `locked`, with the image's current level). Until then the item is `Resolved` with `appliedAt`
  null and `resolvedFromLevel` set; `POST /api/jobs/tick` retries every due one (and escalates expired items), so schedule it every few minutes.
  - Each try claims the item first (attempt count + two-minute lease). A throw (5xx, network, unintelligible answer) is
    transient: backoff 5, 10, 20 ... up to 6h, and after 8 tries the item goes to the Inquisitors (`attempts-exhausted`).
    Untried rows run before those that already failed; a run does 4 at a time within a 45s budget.
  - A retry that finds the image at the settled level under the Knights lock (`KNIGHTS_VOTE_NSFW_LEVEL_REASON`, in
    `@civitai/shared/new-order`) counts as written: an earlier try's answer was lost after the main app applied it.
  - A skip, or an image that is blocked, moderator-locked or at another level than `resolvedFromLevel`, is final and is
    never retried. Blocked or moved: Inquisitor, votes pending again. Moderator-locked: `Closed` with votes graded against the
    moderator's current level (as v1 does when a moderator finalizes), or Inquisitor (`moderator-locked`) when that level
    is unknown. Gone: `Closed`, votes inconclusive. `reason` says which.
  - Once a vote commits, a failure settling it is logged and the player still gets the accepted answer; the item stays
    `Resolved` and the job retries it.
- One judgment: a player judges an image once per question key (`KnightsVote.questionKey`: the rating question's key, or a hidden check's reference question; the same key whatever the item, stage or re-queue), enforced in `insertVote` (`already-voted`, no row, no XP, no gold), under the per-player advisory lock (`lockPlayerVoting`, taken first in `castVote`, the yes/no vote and `insertVote`) because the partitioned ledger cannot carry a unique key on it. A yes/no axis holds several questions per image, so its own (image, prompt) rule applies instead (`ownJudgmentRule`). Index `KnightsVote_playerId_imageId_idx` (migration `20261210120000_knights_v2_tables`, by hand, before deploying Knights) serves the check and `pickHiddenCheck`, which starts at a per-player point in the pool's id range and takes the first unjudged reference from there. Vote pacing (`queue/vote-rate.ts`): `castVote` returns `{ status: 'limited', until }` while the trailing windows in `VOTE_LIMITS` are full, counted from `KnightsVote` itself (no Redis, no state of its own). A per-player `pg_advisory_xact_lock` taken first in the vote transaction, ahead of the item lock, serialises one player's votes, and the limit is re-checked under it, so parallel requests cannot overshoot. Moderators are exempt, and a `QueueDeps` without `voteLimits` is unpaced (tests, the dev simulator). The vote action answers 429 with `lockoutSeconds`; `/play` `load` (`depends('app:play')`) carries `lockoutSeconds`, shown by `$lib/Countdown.svelte`, which re-checks the server when it reaches zero. Vote pacing is checked in Redis before the vote transaction (`lib/server/vote-limits`, `docs/features/knights-vote-limits.md`); the ledger check in `pacingGate` stays authoritative.
- Block reasons (`KNIGHTS_BLOCK_REASONS` in `@civitai/shared/new-order`, `asksBlockReason` in `lib/block-reasons.ts`, migration `20261210120000_knights_v2_tables`, by hand; `KnightsVote.blockReason`, a CHECKed text column): a reason is asked only on the rating question's Blocked answer (feed items and hidden checks alike), which must send one of the original game's five reasons (Inappropriate Minors, Realistic Minors, Depicts Real Person, Bestiality, Other); every other answer sends none. `insertVote` enforces the pairing (`bad-block-reason`, answered 400, nothing written); a hidden check is still graded on the level alone. `/play` opens `BlockReasons.svelte` on the Blocked pill or key (keys 1-5, Esc cancels; covers the answer row on desktop, a bottom sheet at 640px and under) and casts the vote when a reason is picked. Acolyte apprenticeship answers ask for none. The Inquisitor card in the moderator app shows the most common reason among the Blocked votes (a tie goes to the earliest vote's reason).
- Skips (`lib/server/skips.ts`, `?/skip` on `/play`): a Skip button, Space, and the page's own image-error check all post the sealed token to one action. It is not a vote: no ledger row, pay, accuracy or Watch credit, and no pacing. The token's kind and id go into a per-player Redis sorted set (`knights:skipped:<id>`, newest 1000, 90 days), and `getFeed`, `pickHiddenCheck` and `pickYesNo` take it as `exclude`. Every kind is recorded and answered alike, so a skip does not reveal a hidden check; a skipped check is never graded, and the slot still yields a hidden check while the pool lasts, so skipping does not lower a player's rate. A store that is down serves as if nothing was skipped. The apprenticeship has no skip.
- Optimistic judging (`routes/play/optimistic.ts`, `next-item.server.ts`, `GET /play/next`): while an item is on screen the page fetches the one after it (`pickItem`, the same hidden-check/yes-no/queue order `load` uses, leaving out the items named in `after`; the hidden and yes/no rolls are seeded from those items through `slot`, since the last-vote slot has not moved yet). A vote or skip then swaps to it at once and posts `?/vote`/`?/skip` in the background; a refused or lost post shows a short notice, and only a pacing lockout, a redirect or an error reloads the page. With no item ready, or without JS, the form posts and reloads as before. The page keeps up to 10 items ahead (`BUFFER_TARGET`) in two layers: all have their image requested at low priority at the same `src` the stage uses (so it lands in the HTTP cache; the `Image` is dropped once loaded), and the first 3 (`READY_TARGET`) are also decoded and held; consuming one promotes the next into the decoded window, and a swap only goes to a decoded head. A refill (`GET /play/next?count=10-size`, one request at a time, `count` capped at 10) runs whenever 5 or fewer are buffered (`REFILL_AT`); `after` carries up to `MAX_EXCLUDED` (24) tokens, about 2.5 KB of URL, so it stays a GET. An image that will not load or decode is added to `after`, not offered again. `imageUrl` asks the CDN for `anim=false,width=N,optimized=true` (WebP, about a quarter of the bytes of the plain `width=N` JPEG). A feed token is sealed afresh with a random IV on every serve, so the client never compares tokens: every picked item carries `item.key` (`itemKey(question.key, image src)`, computed in `pickItem`, no item id in it) and the buffer, the vote tracker and the page's "already sent" checks use it. A server item whose key was already sent (its background vote still in flight) is not shown or posted again: the buffered item takes its place, or the page shows the "already judged" notice without a round-trip. The server still validates every post. Restart career is in the account menu (`AppHeader`, red "Restart career…" above Sign out, shown to anyone with a `NewOrderPlayer` row via the layout's `isPlayer`), not on `/home` or the Codex: `RestartCareerDialog` loads what a restart takes with `GET /career` and confirms with `POST /career` (`routes/career/+server.ts`, JSON `{ ok, to }` or `{ ok: false, message }`).
- The vote ledger is partitioned by month. `POST /api/jobs/partitions` creates the next months and a vote creates its own month if missing; `POST /api/jobs/tick` also escalates items past `expiresAt` and settles votes on final items (`settledVotes` in its response; a step that throws (including the Conversion steps below) returns 500; items that failed inside a step (a payout, a rating write-back, a yes/no close, a career reset, a shop Buzz grant retry) are retried by the next tick and only counted in `knights_tick_item_failures_total` and logged as `knights-tick-item-failures`, so one bad item does not fail the tick; the response also carries `conversionsRetried` and `labels`). Both need
  `Authorization: Bearer $JOBS_TOKEN`.
- The user guard in `hooks.server.ts` skips exactly the routes in `JOB_PATHS` (tick, partitions, harvest, notify); a new job route must be added there. `POST /api/jobs/notify` sends the opt-out daily-loop notifications (`src/lib/server/notify`, table `KnightsNotificationSend`, migration `20261210120000_knights_v2_tables`, by hand): see "Knights of New Order daily notifications" in `docs/features/notifications.md`.
- `/play` is the voting page: a 3px Watch hairline under the header (`$lib/WatchHairline.svelte`), a meta row (Watch, streak, hearts) below 1200px and a single right rail from 1200px (`routes/play/PlayRail.svelte`: Watch ring, streak, hearts, this week's fervor with board position and gap, next-rank progress, today's judgments across the Order; data from `railFor` in `lib/server/rail-runtime.ts`, the daily board cache plus a 60-second count of `KnightsPlayerDay.votes`), and the apprenticeship meter for Acolytes (a muted Acolyte keeps the meter too). The Watch in the rail and the meta row moves at once when a vote is cast, and the vote that completes it shows the completed Watch (green check, "Watch complete") and the streak +1 at once (`withVotesSent`, `watchStrip`), and a player under their own rank's accuracy bar gets a cue there (`belowBarCue`) linking to the Codex. The header carries a gold popover (earned, pending, Buzz value at `CONVERSION.goldPerBuzz`; the pill is spendable gold, as in the shop, with pending in its tooltip) and an XP gauge popover (`$lib/HeaderStats.svelte`), and the avatar wears the rank badge (Trophy cosmetics 858/859/860/4208 through `lib/server/rank-badges.ts`; a missing one shows the crest). Acolytes get the apprenticeship instead of the feed and cannot vote; a user with no `NewOrderPlayer` row is redirected to `/home` to join (see Joining), as is `/judgments` (`requireMember`, `lib/server/membership.ts`), and an apprenticeship answer from such a user is refused; Knights and above keep the feed. It also shows the Daily Watch (see Daily loop); the Codex's ranks section lists each rank's daily gold cap. Hidden checks and smites: [`docs/features/knights-hidden-checks-and-smites.md`](../../docs/features/knights-hidden-checks-and-smites.md) (migration `20261210120000_knights_v2_tables`, by hand; values in `hidden/config.ts`, env, and `smites/config.ts`). Never put a raw item id in the page: every feed item is a sealed token (`feed-token.ts`), and a hidden check is an ordinary `KnightsVote` (negative `itemId`, graded later by `settleHiddenChecks`). Active smites are the pending record of a career reset; the tick retries it. Yes/no questions (`KnightsQueueItem` rows with an `audience`, served in stretches, labelled per answer, `pnpm run import:yesno <csv>`; CSV columns in `docs/features/knights-yesno-questions.md`): [`docs/features/knights-yesno-questions.md`](../../docs/features/knights-yesno-questions.md) (migration `20261210120000_knights_v2_tables`, by hand, before the import). The notify job's new-images check counts rating items only.
- Routes: `/` is the signed-out welcome page, `/home` the signed-in home, `/play` judges, `/codex` is the rules. The header's primary nav (`lib/PrimaryNav.svelte`: tabs, a fixed tab bar at 75rem and under) reads one list, `NAV_ITEMS` in `lib/nav.ts` (`also` keeps tab-less pages such as `/judgments` lit under their parent). Pages carry no back links; navigation keeps normal history, and the only guards are on `/play`: the "Leave your Watch?" confirm (`lib/leave-guard.ts`) and a `beforeunload` prompt while votes are still queued. Welcome-page pointer effects (`lib/pointer-fx.ts`) switch off for touch and reduced motion.

## Banned and muted accounts

`getStanding(db, userId)` (`lib/server/standing.ts`) reads the database, never the session. Banned, deleted or with no User row: the closed page (403) on every route except the job routes. Muted: may view and convert gold, but `vote`, `skip`, `apprentice` and `POST /career` (restart) answer 403. Detail: [`docs/features/knights-standing.md`](../../docs/features/knights-standing.md). The account menu carries "Back to Civitai" (`CIVITAI_APP_URL`) and "Sign out" (`/logout`, a GET).

## Joining

`/home` shows "Join the Order" to a user with no `NewOrderPlayer` row: a sensitive-content warning (explicit imagery regardless of the user's browsing level), then the `join` action, which requires `accepted=yes`, calls `joinOrder` (`lib/server/join.service.ts`, the only place an Acolyte row is created; idempotent, never touches an existing row) and redirects to `/play`. `/play` redirects a user with no row back to `/home`. The v1 Acolyte badge cosmetic is not awarded here yet. `/codex` is the player-facing Ranks + Rules page (`routes/codex`, anchored sections: ranks, judging, daily, fervor, rating-guide, career; `/ranks` and `/rules` answer 308 to `/codex#ranks` and `/codex#judging`). Its numbers come from `rulesFacts()` (`lib/server/rules.ts`), `rankTable()` and `ladderRows()` (`lib/server/ladder.ts`, passes an optional `minDaysPlayed` through), which read the apprenticeship, progression, daily, fervor and rank config; the rating guide reads the shared level labels. Update the page when a rule changes. Vote pacing is deliberately not described there (public repo).

"What's new" (`$lib/WhatsNewDialog.svelte`, copy and `ANNOUNCEMENT_URL` in `$lib/whats-new.ts`): a one-time launch dialog for members, shown on whichever of `/home` or `/play` they open first (both loads read `whatsNew` from `readNotices`, both answer `?/dismissWhatsNew`, the root layout renders it). A player with v1 progress (`isReturningPlayer`: any XP or a rank above Acolyte) gets the "what changed" copy; a newcomer gets a welcome that explains how the Order works (`whatsNewCopy`). It comes before the rating guide: while it is unseen `readNotices` holds back the guide and progress notices. Got it, Escape and the backdrop close it at once and write a per-user browser marker (`knights:whats-new-seen:<userId>` in localStorage); the layout posts the dismiss in the background, re-reads the page once it is stored (so the guide follows), and while the server still sends the copy to a browser whose marker says seen it is re-sent instead of shown (`whats-new-dismiss.ts`). The marker is read only after hydration, so the dialog is never server-rendered and a no-JS client does not get it. Seen state on the server is the `whatsNew` flag in `knights:seen:<userId>` (`lib/server/seen.ts`; a record without it reads as unseen); delete that key and the browser marker to see it again locally (this also shows the guide again).

## Progression (`src/lib/server/progression`)

Migrations `20261209120000_knights_new_order_player_and_link_review` (`NewOrderPlayer.goldPending` / `goldEarned`) and `20261210120000_knights_v2_tables` (`KnightsVote.xp` / `settledAt`), applied by hand. Progression amounts are in `progression/config.ts`; the Watch, streak and shield amounts are in `daily/config.ts` and the per-rank daily gold cap is in `ranks.ts` (see Daily loop).

- A vote pays the vote XP at once and records `gold` as pending on the vote and in `goldPending`: base x the voter's rank multiplier x `RATING.belowBarFactor` while below the bar, then clamped to what is left of the rank's daily cap (see Daily loop). A clamped vote records the clamped amount, so settling drops or keeps only that.
- `settleItemVotes` pays a graded item once, only when its outcome is final (`Closed`, or `Resolved` and written back): correct = bulk XP, gold moves pending -> earned; wrong or inconclusive = gold dropped. `settledAt` plus the row lock make it idempotent. It runs in the transaction of every Knights path that finalises an item, and `POST /api/jobs/tick` sweeps (`settleFinalItems`) what other apps closed (the moderator app's rulings).
- Fervor is never stored: v2 does not write `NewOrderPlayer.fervor`, which the original game's `newOrderDailyReset` job rewrites for every player. It is read from the vote ledger, the player's graded settled votes **cast** in the last `PROGRESSION.fervorWindowDays` (7) days, no cap, since `startAt` (`progression/fervor.ts`, `fervorLedgerOf`; the status line computes it live). `createdAt` prunes the monthly partitions and matches the original board. The partial `(createdAt, playerId) INCLUDE (verdict)` index for the board's grouped read is in `20261210120000_knights_v2_tables`; one player's read uses `(playerId, createdAt)`. Accuracy and rank do not decay: they stay on `ledgerOf`, the last `PROGRESSION.accuracyWindow` (500) graded votes. A career restart does not touch the column either; `startAt` voids the earlier votes.
- Level curve (`progression/levels.ts`, Knights' own; `@civitai/shared/new-order-levels` is the original game's and must not change): 250 XP for level 1 to 2, each level costing 1.18x the one before up to level 20 (20 starts at 30,594 XP, as in the original), then 1.06x per level. Level 21 starts at 35,757 XP, 50 at 438,370, 90 at 5,020,501; `MAX_LEVEL` is the last level that fits the Int `exp` column. Levels are derived from `exp`, so changing the curve moves players without a migration.
- Ranks: `progression/rating.ts`, knobs in `config.ts` (`RANK_LADDER`, `RATING`). Bands: Acolyte levels 1-20 (the apprenticeship), Knight 20-49, Templar 50-89, Paladin 90+. A rank needs its level, its accuracy bar and `minDaysPlayed`: Paladin asks for 60 distinct UTC days with a vote since `startAt` (`daysPlayedOf`: `KnightsPlayerDay` rows with `votes > 0` on or after the `startAt` date, read at rank-up only when level and accuracy already earn a day-gated rank, and for the status line of a player whose next rank has one). Accuracy reads `ledgerOf` (last 500 graded votes, not time-bound) and is "not yet rated" below `RATING.minGraded`.
- `/leaderboard` (`leaderboard.ts`, in the avatar menu): the rolling weekly board, from `KnightsVote`, `NewOrderPlayer` and `User` only (not the main app's `Leaderboard` tables). Knight, Templar and Paladin with fervor > 0, highest first (lower user id on a tie), banned and deleted accounts left out, top `LEADERBOARD_SIZE` (100) plus the viewer's own position when outside them. The whole ranked list is built by one grouped read at most every 5 minutes (`BOARD_FRESH_MS`; the first request after that rebuilds it, and a stored board carries its `builtAt` stamp so an older one is rebuilt) and kept in process memory and in sys Redis (`knights:leaderboard:<UTC date>`, 5-minute TTL, `leaderboard-cache.ts`; every Redis call is raced against a 400ms clock and a down store just means a direct read; one build per process, two instances may each build once per window; the page says "Updated N min ago"). The page shows a podium for the top 3, rows from 4 down, and the viewer's standing with the gap to the place above (`standingGap`), plus a collapsible "How fervor works" panel whose numbers come from `PROGRESSION` (`leaderboard-view.ts`); "Updated N min ago" is counted live on the client from `builtAt` and the server clock (`$lib/updated-ago.ts`). Each row shows the avatar (the profile picture when its `nsfwLevel` is 1–16, else `User.image`; `Avatar.svelte`), and the rank's badge cosmetic image (`Cosmetic.data.url` of 859 Knight / 860 Templar / 4208 Paladin, read in the same build); a missing or failed image shows `RankEmblem`.
- Rank-up runs in `settleItemVotes` after XP is added; it can skip ranks and never demotes, and never touches Acolyte or Inquisitor.
- Migration `20261212120000_knights_v2_paladin_rank_enum` (by hand, after the main app with the `Paladin` client is deployed, before Knights: an old Prisma client throws on the Paladin `NewOrderRank` row, and Knights' `rankType = 'Paladin'` queries fail without the label): enum value plus `NewOrderRank` row.
- `/dev/simulate` 404s unless SvelteKit's build-time `dev` is true; it also has "Set level" (`dev/set-level.ts`) and shows accuracy. "Set level" only sets `exp`, then applies the normal rank-up, so it cannot make an unrated player a Templar or Paladin: a rank needs an accuracy over at least `RATING.minGraded` (50) graded votes, and Paladin 60 distinct days played. Cast graded votes as that player first to build that record.
- XP is also added to the original game's Redis exp counter (`new-order:exp`, only when that player's field is present) after the commit, while both games run: its nightly reset overwrites `NewOrderPlayer.exp` from that counter, and an absent field is re-read from Postgres, which already holds the XP.

## Daily loop (`src/lib/server/daily`)

Tables `KnightsPlayer` (streak, shields, recap dismissal, popup opt-out) and `KnightsPlayerDay` (votes, gold recorded, Watch, bonus per UTC day), migration `20261210120000_knights_v2_tables` (applied by hand, before deploying). Knobs: `daily/config.ts`; the per-rank gold cap is `dailyGoldCap` in `RANK_RULES` (`ranks.ts`). Days are UTC strings (`days.ts`); logic takes the clock as an argument.

- `castVote` calls `recordVoteDay` only after locking the player's `NewOrderPlayer` row; that lock is what makes the day row safe. The streak bonus is earned gold, not cap gold. The daily gold cap is on gold recorded at vote time (`goldRecorded`, "Gold recorded today"): a vote graded wrong later forfeits its pending gold but does not release cap headroom.
- Streak and shields are pure (`streak.ts`). A shield is granted lazily per ISO week and spent when the next Watch completes, covering exactly one missed day. `liveStreak` shows what that completion would find.
- The recap (`getRecap`) is read from the vote ledger for the last play day before today, so it keeps changing as votes settle (Confirmed + Missed + Undecided = cast: Undecided is every vote without a verdict, pending or settled inconclusive); dismissal is stored per day on `KnightsPlayer`. There is no automatic popup any more: the home page (`/home`) shows it as the "Yesterday's verdicts" card (`$lib/VerdictsCard.svelte`, figures from `$lib/recap-view.ts`, `findRecap`), and the header button (`$lib/RecapButton.svelte`) reads `GET /recap` on click and opens `$lib/RecapDialog.svelte`. Either one marks today's recap seen (`POST /recap` stores the per-day dismissal and leaves `recapPopupOptOut` alone: the column and `getRecap` are kept but nothing renders or reads the opt-out). The header dot comes from `getRecapState` in the root layout load: a play day before today exists and today's recap has not been seen.
- A career reset moves `NewOrderPlayer.startAt`: a streak whose last Watch was completed before it is treated as 0 (shields kept), only votes cast since it count toward the Watch, and the recap ignores earlier votes. The gold cap still counts the whole UTC day.

## Conversion (`src/lib/server/conversion`)

Gold -> Buzz, the label pass and the tick's retries. `CONVERSION.goldPerBuzz` is 20 (the shop's anchor, 20 gold = 1 Buzz); the header's Buzz value reads it. Buzz is only bought per shop pack (there is no straight gold-to-Buzz conversion). Conversion is on by default; the kill switch `KNIGHTS_CONVERSION_DISABLED` (`conversionEnabled()`) set to `true`, `1`, `yes` or `on` (any case) turns it off, and Buzz packs are then refused (the rest of the shop still sells). Apply by hand, in order: `20261209120000_knights_new_order_player_and_link_review`, `20261210120000_knights_v2_tables`, then deploy the main app, then Knights (never earlier: the previous main app's reset does not zero `goldEarned`). Detail: [`docs/features/knights-conversion.md`](../../docs/features/knights-conversion.md). The gold shop (`/shop`, `src/lib/server/shop`, tables `KnightsShopItem` and `KnightsShopPurchase`, migration `20261210120000_knights_v2_tables` by hand, `KNIGHTS_SHOP_DISABLED`; spending adds to `NewOrderPlayer.goldConverted` under the player row lock): [`docs/features/knights-shop.md`](../../docs/features/knights-shop.md). The catalog is managed in the moderator app, `/knights-of-new-order/shop` (own page grant; `apps/moderator/src/lib/server/knights/shop-catalog.service.ts`), and every edit is recorded in `KnightsShopItemChange` (same migration). Item ids are serial integers. The rotation lives in `@civitai/shared/knights-shop`, so the page's preview draws the same rotation and deals Knights does (it flags items Knights would hide, and cannot show whether Buzz packs are closed).

## Reference images and the apprenticeship (`src/lib/server/trials`, `src/lib/server/apprenticeship`)

Tables `KnightsReferenceImage`, `KnightsHarvestCursor` (migration `20261210120000_knights_v2_tables`, applied by hand) feed the Acolyte apprenticeship. Harvest knobs are in `trials/config.ts`.

- A reference image has a known `answer`, a `source` (`core` | `harvested`; `agreement`, from Templar/Paladin agreement, is a later source) and a `pool`. `imageId` is unique across modules on purpose: one known answer per image, and an image sits in `trials` or in `hiddenCheck`, never both. Core rows are curated in the moderator app, `/knights-of-new-order/trials` (own page grant; `apps/moderator/src/lib/server/knights/coreset.service.ts`), and need an `explanation`. `status` is `active` (served), `pending` (held for the blind spot-check, never served) or `retired`; the same page flags items by failure rate (`coreset.config.ts`).
- `POST /api/jobs/harvest` (`Authorization: Bearer $JOBS_TOKEN`) reads `ModActivity` rows `setNsfwLevel` on images past a cursor, no older than `maxRulingAgeDays`. It keeps an image only while the moderator ruling still stands and its image is still servable (`servableImage`; see `harvest.service.ts`). Images already present are skipped. It also retires fresh items older than `freshMaxAgeDays` or whose image moved. Safe to run repeatedly; schedule it daily. With `spotCheck` on, harvested Trials-pool items are inserted `pending` (hidden checks stay `active`) until a moderator re-rates them blind: the same rating makes them `active`, any other retires them, and an unchecked one retires with the other fresh items when it ages out.
- The apprenticeship (continuous graded stream of core, harvested and moderator yes/no references in `KnightsYesNoReference`; XP per right answer; Knight at level 20 with 75% over the last `APPRENTICE.window` answers; recap every 20) is described in [`docs/features/knights-apprenticeship.md`](../../docs/features/knights-apprenticeship.md). Answers live in `KnightsApprenticeAnswer` (migration `20261210120000_knights_v2_tables`, by hand, then deploy Knights and moderator); an answer outlives its reference (FKs `SET NULL`, snapshot `imageId` + `questionKey`).
- Rank badges: apprenticeship promotion and the Progression rank-ups call `grantRankBadges` (`progression/badges.ts`), which inserts the Knight (859), Templar (860) and Paladin (4208) Trophy cosmetics into `UserCosmetic` (hardcoded ids, the first two from the main app's `newOrderConfig.cosmetics.badgeIds`; no table maps rank to cosmetic), once per player, best effort, and a skip to Paladin also grants the Templar badge. It does not queue the user-search reindex the main app's `grantCosmetic` does. The v1 rank-up signal (`NewOrderPlayerUpdate`) is not sent. Watch-streak badges (7/30/100 days) are granted by the same insert on the Watch that reaches them (`grantStreakBadges`; ids in `daily/streak-badges.ts`, a null id is skipped). Level and Founding Knight badges are not granted.
- `answers` and `failures` are per-item counters.

## Motion and sound (`src/global.css`, `src/motion.css`)

Tokens and easings are in `src/global.css`, keyframes in `src/motion.css`. Keep play-loop motion to 200ms or less and never gate a submit on it; every keyframe needs a reduced-motion counterpart; a new sound needs both files, `SOUND_NAMES` and `SOUND_LEVELS` entries and a `CREDITS.md` line. ## Deploy

`Dockerfile` (adapter-node, user 1001, port 3000, `node build`) builds from the repo root: `docker build -f apps/knights/Dockerfile .`; its only build-time env is a placeholder `DATABASE_URL`. `GET /healthz` (`src/routes/healthz`) is the probe: 200 `ok`, no database, Redis or Flipt, and `hooks.server.ts` exempts that exact path (apart from `JOB_PATHS`) from the guard, the access gate and the standing check. `GET /metrics` is exempt the same way (see Metrics).

## Metrics

`GET /metrics` serves Prometheus text to in-cluster scrapes only. Every metric, its labels and meaning, and the gauge queries: [`docs/features/knights-metrics.md`](../../docs/features/knights-metrics.md). Labels are bounded enums, never user, image or item ids; add a new metric there too.

## Tests

`pnpm --filter @civitai/knights-app test` (project `app:knights`). Typecheck with `typecheck`, never `check`. Run the app on port 5180 with `cd apps/knights && pnpm dev --port 5180 --strictPort`. `pnpm dev -- --port 5180` lands on 5173 (the `--` ends Vite's option parsing), and without `--strictPort` it silently picks another port when the one asked for is taken.
